# Saksı Pilotu firmware

ESP32-S3 DevKitC N16R8 firmware (PlatformIO + Arduino). Phase 1: measure the soil,
air and light sensors, buffer the readings and upload them to `/api/ingest/batch`.
Requirements and pin plan: `docs/prd/2026-10-07-saksi-pilotu-sensor-sulama-yerel-llm.md` §5–§6.

## Layout

| Path | What |
| --- | --- |
| `lib/core/` | Board-independent logic: ring buffer, soil %, timestamps, batch JSON, upload backoff, console parsing. No Arduino headers, so it runs on the host. |
| `test/test_core/` | Unity tests for `lib/core` (`pio test -e native`, needs gcc). |
| `src/` | Board code: NVS settings, sensors, uploader, serial console, `main.cpp`. |
| `include/root_ca.h` | Root certificates for the cloud API, generated by `scripts/gen_root_ca.py`. |
| `scripts/version.py` | Sets `FW_VERSION` (CI: `FIRMWARE_VERSION`; locally: git commit). |

## Build

```bash
pip install platformio==6.2.0
cd firmware
pio test -e native     # host unit tests (Linux/macOS, or Docker on Windows)
pio run -e esp32s3     # board image
pio run -e esp32s3 -t upload && pio device monitor
```

CI (`.github/workflows/firmware.yml`) runs both. Every firmware change merged to `main`
also becomes a GitHub release (`fw-<sha>`) with the images and a `manifest.json` of their
offsets. Flash them at their own offsets, never as one merged file and never with an erase:
NVS at 0x9000–0xE000 holds Wi-Fi, the token and the calibration.

## Installing from the browser

The web app's `/kurulum` page (Chrome or Edge on a desktop) writes the latest release without
erasing, then talks to the serial console: Wi-Fi and token form, live log, soil calibration.
It needs no account and never sends the token anywhere but the board. ESP Web Tools isn't
used because it erases the whole flash on boards without Improv Serial.

## First-time setup

Plug in the board's **USB** port (not "COM") and open a serial terminal at 115200 baud.

1. In the web app, open the greenhouse, **Add board**, and copy the token (it's shown once).
   Add a channel for every enabled sensor below. A reading from a channel that isn't
   registered makes the server reject the whole batch (`400`).
2. On the board:
   ```
   wifi "Network name" "password"
   token <nodeId>.<secret>
   status
   ```
   `status` should show Wi-Fi connected, the clock synced and, within a minute,
   `last HTTP 204`.

Default channels: `soil1` (GPIO4), `air_temp` `air_humidity` (AHT25) and `light` (BH1750);
the AHT25 and BH1750 share the I²C bus at GPIO8/9. More probes go on `soil2` `soil3` `soil4`
(GPIO5/6/7), off by default: register the channel in the web app first, then `channel soil2 on`.

## Calibrating a soil probe

1. `raw` with the probe in dry air: note the mV of the channel (the **dry** value).
2. Probe in a glass of water up to the line: `raw` again (the **wet** value).
3. `cal soil1 <dry> <wet>`, e.g. `cal soil1 2850 1290`.

Until then the defaults (2800 / 1200 mV) give only a rough %.

## Behaviour worth knowing

- No readings are taken until NTP has set the clock; timestamps are UTC.
- Readings wait in a RAM ring buffer (100 000 in PSRAM, about 8.7 days at the 4 default channels).
  When it's full the oldest are overwritten. A power cut empties it.
- Upload failures back off from 10 s to 5 min; a `400` batch is dropped so it can't
  block the queue. The board never restarts because of Wi-Fi, only the task watchdog
  (60 s) resets it.
- `insecure on` skips the TLS certificate check. It's for the bench only; `status` shows
  it while it's on.
